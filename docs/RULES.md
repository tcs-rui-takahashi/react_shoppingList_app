# 運用ルール（RULES）

## PR 運用方針

**内容・方針**

- PR 名は目的や範囲がわかるように具体的に記載する。
  - 例：`phese0-3:初期レイアウト作成`
- PR テンプレートを活用し、変更概要・目的・テスト内容を明記する。
  - テストおよび型チェック項目を必須とする。
  - ユーザーが見える挙動（UI / 操作 / 表示）と、内部ロジック（hooks / validation など）の両方を対象とする。

**背景・理由**

- 明確な命名により、レビュー対象を瞬時に把握できる。
- テンプレートの利用により、レビュー観点の抜け漏れを防止する。

---

## 型運用

**内容・方針**

- 型定義は一括管理し、共通モジュールで扱う。
- 新規型追加時は既存との重複を避ける。

**背景・理由**

- 設計段階で型を共有し、後続機能の拡張を容易にする。

---

## ディレクトリ構成

**内容・方針**

- `apps/` と `tests/` の構造は一致させる。
  - 現状のファイル構造を参照
- `hooks/` や `utils/` などの共通フォルダは `apps/` 配下に配置する。

**背景・理由**

- 構造の統一により、テストコードとの対応関係が明確になる。
- ディレクトリ階層を明確化し、保守性を高める。

---

## 命名ルール

**内容・方針**

- 型ファイルとロジックファイルを分離する。
  - 型定義：`*.type.ts`
  - ガード・判定ロジック：`*.guard.ts`

**背景・理由**

- 型とロジックの責務分離により、カバレッジ精度と保守性を向上させる。
  - 型定義ファイルはテスト対象外に設定しており、もしロジックを書いてしまうとカバレッジが不正確（低く）表示されてしまう。
